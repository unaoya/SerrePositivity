## 1. 採用を提案する層順序

`Core < Foundation∞ < Stable.Base < F2 < Stable.F2Applications < Derived < KST`

- Foundation∞ は **既存 F1・F1B・汎用 HomotopyLimits を同じ意味上の層**に置く。
  新たな一括ディレクトリ移動や `Foundation∞.lean` という巨大集約は要求しない。
  F1→F1B90辺、F1B→F1 137辺は共通層内の依存として文書化し、現在のファイル単位 DAG を維持する。
  F1→HL83辺、HL→F1 264辺、HL→F1B127辺も同様。F1B→HL3辺も同一層内になる。
- **汎用 HomotopyLimits は F2 より前**。filtered/sifted/Ind/presentable を具体的に扱う接続は F2 側へ分離する。
  `HL < F2` を反転する案は F2→HL359辺を新たな逆辺にするため採らない。
- **Stable 基礎は F2 より前**。IsStable・exact・安定圏の有限極限／余極限を F2 の Ind 安定性などが消費する。
  ただし Stable→F2 が42辺あるため、Stable 全体をそのまま前へ動かす案でも解決しない。
- 一般 quasicategory の錐・slice・関手同型・pointed 圏の補題は Stable の名前にかかわらず Foundation∞ へ抽出する。
  IsStable を定義する前提の zero/fiber/cofiber の図形も、定義と独立なものはこの一般層に属する。
- 真に F2 の冪等完備化・濃度・生成を使用する安定圏の結果は `Stable/F2Applications/`（提案）へ。
  Stable.Base は同ディレクトリ・F2・Derived・KST を推移的にも読まない。
- Core は F1/F1B/HL/F2/Stable/Derived への直接辺が現在0であり、この境界を維持する。
  F1B を使う core の補題を、名前だけで Core へ移してはならない。

これはディレクトリ名を全順序に並べる案を修正するもの。共通層の内部まで F1<F1B とするなら、
54個の直接参照先だけでなく F1B 内依存閉包215本の再配置・分割が別に必要となる。
その追加の細分化は今回の層境界修復の必須条件にしない。任意の上位依存を許す例外でもない。

旧パスの shim が必要でも、下位利用元は新正本を直接読む。shim 経由の逆参照で層監査をすり抜けない。
検証は新層境界の直接辺と推移閉包、移動先全モジュール、既存公開型、監査被覆を確認し、最後に `scripts/refactor/verify.sh`。
verify.sh は孤立 olean の除去・全体／監査対象の build・監査・sorry 閉包を含むため、今回の読み取り調査では実行していない。
残存例外があれば全件を報告する。辺数の減少だけで「層順序確定済みの実装」とは報告しない。

## 7. A〜E の評価

- A 数学：定理・名前・型を保持する配置変更が中心。一般四角形と zero 専用部、Kan と spectrum を混同しない。
- B 整合：F1/F1B/HL は共通層、Stable 基礎は F2 の下、安定 Ind／完備化の接続は上という境界を提案。
- C 実装：既存 move_module.py を流用。過大 import の分割が先で、閉包の一括下方移動は不可。
- D 工数：136〜268h の暫定値。重複候補を統一した枠であり、599辺ごとの時間を加算した値ではない。
- E リスク：active WIP・公開集約の import 互換性・推移的な DG/Sp 依存。代案は当面の個別例外だが、各行の解消先と監査を必須にする。
