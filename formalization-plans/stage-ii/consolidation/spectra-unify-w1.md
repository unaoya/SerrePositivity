## 0. 背景

宣言を依存関係で整理した結果（`research/cleanup-zero-base/`）、対称スペクトルは三つの層になっていた。

- A：一般の理論。`CategoryTheory/Monoidal/Mod/`、`CategoryTheory/Enriched/`、`Spectra/SymmetricSequence/`。数学の中身はほぼここにある。
- B：`Spectra/General/`（`GeneralSymmetricSpectrum C K`、畳んだ後 341 宣言）。A に Sym(K) 上の加群を当てはめたもの。
- C：`Spectra/SymmetricSpectrum/`（`SymmetricSpectrum`、660 宣言）。A に球面の対称列上の加群を当てはめたもの。B の特殊な場合（C = 基点付き単体集合、K = 円周）だが、B を経由せず A からもう一度作ってある。

C の 660 宣言のうち 416 は、一行の言い換え（一行の定義 211、`rfl` の定理 74、補題一つの適用 131）。`Spectra/General/SimplicialComparison.lean` には `simplicial_type : GeneralSymmetricSpectrum PointedSimplicialSet circle = SymmetricSpectrum := rfl` をはじめ、B の特殊化が C と一致するという `rfl` の比較が並んでいる。

目標の形：B を対称スペクトルの唯一の定義にし、C は「B で基礎圏を単体集合、座標を円周にしたもの」とする。C に残るのは、単体集合に固有の内容だけ。

材料：`research/cleanup-zero-base/spectra/decls.jsonl.gz`（B・C・`CategoryTheory/Enriched`・`Adjunction/Comparison` の全宣言。型、型の中で使う宣言、値の中で使う宣言、ソースの位置）。`dump.lean` で採り直せる。

## 1. 進め方の規則

- **一回の依頼は一段だけ**。段の終わりでコミットし、報告を書いて止まる。次の段は調整役の連絡を待つ。
- 変えないもの：文献の対応表（`research/*-coverage/` の `review/*.csv`・`external.csv` など）が名指しする宣言の名前と主張。段の最初に、対象の宣言が名指しされていないかを自分で確かめ、結果を報告に書く。
- それ以外の宣言は、名前も主張も変えてよい。消してよい。範囲の外の使用箇所（`Spectra/ModelCategory`、`Spectra/Stable`、`scripts/` の監査・検査など）は、同じ作業の中で直す。
- 判断に迷う所、指示にない削除や範囲の拡大が要る所は、進めずに報告に書いて止まる。
- ビルドは `--class bulk` の鍵で、対象と、それを import する側だけ。root 全体は調整役。⑦ が別名の削除で全体を建て直している間は、鍵を待つ。
- 判定（各段共通）：対象と使う側のビルドが通る。公理と sorry が増えない。変えた監査・検査が通る。対応表が名指しする宣言の（カーネル名・型）が前後で一致。

## 2. 段 1：基本の部分で、C を B の特殊化に置き換える

対象は、`SimplicialComparison.lean` に `rfl` の比較がある C の宣言（型・`forget`・`level`・`action`・自由スペクトル・評価・`freeAt` とその随伴など）と、それらが置かれている C のファイル。

1. `SymmetricSpectrum` の定義を、`GeneralSymmetricSpectrum PointedSimplicialSet circle` を使う形にする（`abbrev`）。
2. 対象の C の宣言ごとに、次のどれかにする。優先はこの順。
   - **消す**：使う側を B の宣言に直す。対応する `simplicial_…` の比較も消す。
   - **B の宣言の一行の別名として残す**：使う側で引数（`C`・`K`）を毎回書くことになって読みにくくなる場合だけ。理由を記録する。
   - **そのまま残す**：B に対応がなく、単体集合に固有の内容である場合。どこで固有の性質を使うかを記録する。
3. C のファイルで、中身がなくなったものは消し、import を追従する。

この段では、テンソル積・内部 Hom・余テンソル・写像空間・懸垂には進まない（`rfl` の比較があっても、段 2 以降）。段 1 の範囲に入れるか迷う宣言は、入れずに一覧にする。

## 3. 段 2：C の残りの宣言の分類表（Lean は変えない）

段 1（1b9299036）の結果：C は 663 → 622 宣言、6,149 → 5,951 行。段 1 の後に C に残る宣言の全部について、扱いの案を表にして止まる。**この段では Lean・監査を一切変えない**。扱いを決めるのは調整役とユーザーで、実施は次の段以降。

対象は `Spectra/SymmetricSpectrum/` の、ソースに名前を書いてある宣言の全部（自動生成の `_assoc`・`eq_n`・`_proof_n` などは親に含める）。段 1 で残した 15 件（別名 11、残す 4）も含める。

一件ごとに、宣言の主張と証明の本体を読んで次を埋める。名前の一致だけで相手を決めない。

1. **まとまり**：基本・自由・各段のテンソル・テンソル積・内部 Hom・余テンソル・写像対象・懸垂とループ・極限と余極限・その他。ファイル名からではなく、主張の中身から決める。
2. **B（`Spectra/General/`）・一般論（`CategoryTheory/Monoidal/Mod/`、`CategoryTheory/Enriched/` など）の相手**：同じ主張の宣言があればその名前。`SimplicialComparison.lean` などに比較（`simplicial_…`）があればその名前と、比較が `rfl` かどうか。
3. **扱いの案**：
   - **消す**：相手があり、使う側を相手に直せる。
   - **別名**：相手があるが、引数から `C`・`K` が決まらず、使う側で何度も書くことになる。
   - **B に一般版を足す**：相手はないが、主張と証明が単体集合・円周に固有の性質を使っていない。どの仮定で一般化できるかを書く（段 1 の `lift_unique` はこの扱いの候補）。
   - **固有として残す**：単体集合・円周に固有の性質を使う。どの性質をどこで使うかを書く。
   - **判断できない**：理由を書く。無理に上のどれかに入れない。
4. **使われ方**：範囲内の使用者の数、範囲外の使用者の数（`Spectra/ModelCategory`・`Spectra/Stable` など、監査・検査スクリプトは別に数える）、対応表の名指しの有無。数えるときは `Spectra/` を import する全モジュールを読む（root の閉包だけでは `Spectra/` は入らない）。`research/cleanup-zero-base/users.lean` と `dump.lean` を使ってよい。
5. **使用者がどこにもない宣言**は、内容の種類を一つ選ぶ。未使用であることを「消す」の理由にしない。
   - 理論の主張（その概念について文献に書いてあるような命題）
   - 残す定義の基本補題（単位・結合・自然性・成分の式など）
   - 言い換えの間の一致（二つの表示が等しいこと）
   - 他所に同じ内容がある（相手の名前を書く）
   - 使われていない途中の段（何の途中だったかを書く）
6. **証拠**：判断の根拠にした場所（ファイルと行）を一つ以上。

## 4. 段 3：「自由」と「極限と余極限」の実施

段 2 の表（`research/cleanup-zero-base/spectra/stage2.csv`、66c61a21d）の `group` が「自由」「極限と余極限」の 81 件（案：消す 42、別名 25、B に一般版を足す 13、判断できない 1）を実施する。他のまとまりには進まない。`freeFunctor_unitIso`（判断できない）と、自由関手のモノイダル・組紐構造に関わる宣言は、テンソル積の段に回す（触らない）。

表の案は出発点。一件ずつ、次の規則で扱いを確定する。

1. **中身が一行程度の単なる書き換えは消す**（ユーザー 11-20）。定義でも補題でも、本体が他の宣言（B・一般論・Mathlib）の呼び出しにデータを渡すだけ、`rfl`、定義の展開だけ、のものは消して、使う側を相手に直す。使う箇所が多いことは残す理由にしない。
2. **別名は最小限**。残すのは、相手を使う側で直接書くと、引数から決まらない `C`・`K`・球面列などを何度も明示することになるものだけ（段 1 の `freeAt`・`evaluation` と同じ基準）。表で「別名」の 25 件も、この基準でもう一度見て、消せるものは消す。残すものは `abbrev` 一行で、理由を記録する。
3. **B に一般版を足す**：主張と証明を B（表の `destination`）に一般の形で置き、C の版は消す。一般化が通らなければ C に固有として残し、どこで詰まったかを記録する。足す宣言の名前は B の既存の名づけに合わせる。
4. **未使用の宣言**：「他所に同じ内容がある」で相手が実在し、主張が同じことをビルドで確かめられたものは消す。「理論の主張」「残す定義の基本補題」「言い換えの間の一致」は、1 に当たる（一行の書き換え）ものだけ消し、それ以外は残す。
5. 相手が本当に同じ主張かは、使う側を直してビルドが通ること、未使用のものは `example : <C の型> := <相手>` が通ることで確かめる（確かめるための `example` はソースに残さない）。通らないものは扱いを変えて理由を記録する。上限（`maxHeartbeats` など）を上げて通すことはしない。
6. 中身がなくなった C のファイルは消し、import と監査・検査を追従する。変更の前から落ちている検査 11 本は直さない（落ち方が変わらないことだけ確かめる）。
