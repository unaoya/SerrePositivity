# 整理の規則（共通）

2026-11-19 からの整理で、ユーザーと決めた規則をまとめたもの。各領域の指示書（SU-W1、PK-W1 など）は、ここを前提にする。経緯は [cleanup-log.md](cleanup-log.md)。

## 目標

専門家が読んで把握できる状態。ファイルと行が少ないこと。行数は目安の一つで、把握しやすいかどうかはユーザーが判断する。

## 進め方

- 今のファイルやディレクトリを単位にしない。宣言と、宣言どうしの依存から始める。
- 一つの領域ずつ。一回の依頼は一段で、完了の条件を満たしたらコミットして止まる。方向は調整役のチャットでユーザーと決める。
- 先に分類表（何も変えない）、次にまとまりごとに実施。依存の下流の定義を先に揃える（対称スペクトルで、余テンソルの定義を揃えたら、上流で残していた補題が消せた）。
- 領域を一つ、宣言 → ファイル → 文献との対応まで通す。
- 整理が終わるまで、新しい形式化はしない。

## 宣言の扱い

- **対応表（`research/*-coverage/`）が名指しする宣言は、名前も主張も変えない。** 段の最初に照合する。準備の宣言は変えてよい。
- **中身が一行程度の単なる書き換えは、定義でも補題でも消す。** 本体が他の宣言の呼び出しにデータを渡すだけ、`rfl`、定義の展開だけ、のもの。使う箇所が多いことは残す理由にしない。
- **別名は最小限。** 残すのは、相手を使う側で直接書くと、引数から決まらないものを何度も明示することになる場合だけ。`abbrev` 一行で、理由を記録する。
- **随伴の成分（評価・転置・単位・余単位）に付けた名前も消す。** 消した名前、展開後の式、展開の箇所の数を記録する。後で、可読性のために戻すことがある（対称スペクトルでは `loopFunctor` を戻した：文献で名前の付いた関手で、展開が長い）。
- **未使用だからといって消さない。内容で判断する。** 理論の主張、残す定義の基本補題、言い換えの間の一致は残す。他所に同じ内容があり、相手が実在して主張が同じと確かめられたものは消す。使われていない途中の段は、一覧をユーザーに見せてから。
- **一般化できるものは一般の側へ移す。** 足す前に、一般論と移す先に同じ内容がないかを確かめる（対称スペクトルでは、「足す」の見積もりは毎回、実際の二倍だった）。通らなければ固有として残し、詰まった所を記録する。
- **上限（`maxHeartbeats` など）を上げて通すことはしない。**
- `private` は、ファイルの整理が落ち着いてから付ける。
- 削除・Archive への移動・範囲の変更は、ユーザーの承認が要る。

## 確かめ方

- 消した宣言が相手と同じ主張であることは、使う側のビルドか、旧い主張への `example` で確かめる（`example` はソースに残さない）。
- 対象と使う側のビルド。公理と `sorryAx` 依存が増えない。監査・検査の成否が前後で変わらない（以前から落ちている検査は直さず、落ち方が変わらないことだけ確かめる）。
- **ファイルを統合・分割したときの、内部の補助名の差は許す。** Lean がモジュールの中で同じ証明の項を共有して付ける `_proof_*` などは、ファイルをまとめると数が変わる。判定の「宣言の集合が前後で同じ」は、名前を書いた宣言と、その方程式補題などの名前の決まる生成物について満たせばよい。補助名の増減は件数を報告し、それらの名前が本体・スクリプト・対応表・blueprint から文字として参照されていないことを確かめる。過去の実行の記録（`scripts/refactor/targets/` の比較目録、`research/` や `formalization-plans/` の過去の報告、証拠）に名前が残っているのは数えない。数えるのは、今も実行・生成に使われるもの（本体、監査・検査のスクリプト、対応表、blueprint の生成器と生成物）。名前を書いていない宣言（無名の instance）は、名前ではなく（モジュール、ソース上の位置）で前後を対応させる。
- 証拠（ログ）は git の外（`~/serre-evidence/…`）。結果の表は `research/` に。

## 分類と印

- 分類は、主張に現れる概念で決める。ファイル・名前空間・宣言の名前の文字列では決めない。
- 止めた経路の部品かどうか、補助（一つの定理の証明のためだけのもの）かどうかは、分類に使わず印にする。
- 概念の木（`research/cleanup-zero-base/whole/`）は仮の見取り図。領域を整理するときに読んで直す。

## 報告

- 段ごとに、前後の数（宣言、行、ファイル）、扱いごとの件数、見積もりとの差、つまずいた所と対処、使う側の前後の例（短くなった・変わらない・長くなった）、かかった時間。
- 一段ずつ、判定の表（一件一行）を残す。

## 領域の順（11-20 時点）

1. 対称スペクトル（SU-W1、進行中）：C の宣言は済み。C のファイル → B → 一般論 → 使う側 → 文献との対応。
2. Postnikov の類の逆データ（PK-W1）：対称スペクトルを終えてから。二切断版が後続版に n = 1 を入れた一行の包みで、移行の途中で残っている。その後に、同じ型の「共通核」の系。
3. 導来 blowup：評価・導来制限・係数拡大が三系統で並行している、という指摘（本体では未確認）。

監査の作り直し（AR-W1）と、使われていない import とファイルの掃除（IM-W1）は、別のレーンで並行。

## 文献で名前のある定義（11-20、対称スペクトルの段 10 で決定）

- 一般論の一行の適用であっても、文献で名前のある構成（内部 Hom、次数のずらし、Fₙ と Evₙ、懸垂とループ、球面スペクトルなど）は、一行の名前として残す。使う側が一般論の名前を直接書くと、その理論の話として読めなくなる。
- 残した定義についての、定義を開くだけの補題と、一般の補題をそのまま当てはめただけの補題は消す。
- 特別な場合（円周など）にしか使っていなくても、その場合に固有の性質を使っていない内容は、一般の形で書く。
- 名前として残す定義の計算の補題（定義を開く等式）は、消すと使う側が同じ等式を `have` で書き直すことになるなら残す。消すのは、使われていないものと、一般の補題が名前の形のまま直接当たるものだけ（11-20、段 11 の差分を読んで追加：13 箇所で書き直しが生じた）。
- 削除の後は、使う側の差分を読む。行数が増えたファイルは、消し方が合っていない印。

## 一般論を作って適用する（11-21、ユーザーの方針）

- 構造や構成を、使う所でその都度手で書かない。一般論として一度書き、使う所はその適用にする。行が減らなくても、適切な場所に置くことを優先する。
- 領域を整理していて一般論が出てきたら、その一般論を土台として先に整える（豊穣化は EN-W1）。
- 一般論を足す前に、その層の現状の表（宣言、使う側、主張が何を使っているか）を作る。「ほかでも使える」と言う前に、数学としてどのやり方かを区別して確かめる。

## 構造の登録（11-21、LI-W1）

- 一つの型に、その種類の構造が一つしか無いものは、定義した所で全体の instance として登録する。使うファイルごとに局所 instance として置き直さない。
- 同じ型に複数の構造がありうるもの、仮定つきで推論に載せにくいものは、scoped instance にする。
- Mathlib の作法があるもの（導来圏の選択は変数 `[HasDerivedCategory C]`）はそれに従う。
