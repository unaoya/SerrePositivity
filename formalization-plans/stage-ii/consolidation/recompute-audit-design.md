# AR-W1 再計算監査の設計案

記録監査は毎回動かす。再計算監査は、同じリビジョンについて Lean が観測した宣言・公理・環境依存の条件を照合する。段3では全宣言の公理比較を実装する。以下の環境依存の検査と核再検査は、別の試作で時間と検出範囲を測って決める。

## 1. 再計算するもの

環境依存の検査は、段2の [R5 の規則表](review-audit-zero-base.md#4-r5-の規則と機械で判定できる範囲) のうち Lean で調べる項目を対象にする。

| 検査 | 案 | 所要時間の見積もりと計測方法 |
| --- | --- | --- |
| 全宣言の公理・直接未証明入力 | 公理集合は全対象を比較する。モジュールを import し、所有元付きで Lean の `collectAxioms` を得る。直接の `sorryAx` は別の検査として、変更された宣言の型・値を調べ、許可された親と照合する。 | 段3の全公理比較は360,168宣言、Lean 667秒。起動・環境構築・走査・出力を計測し、ビルドと鍵待ちは別に記録する。直接の `sorryAx` の追加走査は変更分で計測する。 |
| 使われていない仮定 | 変更された安定 API と主定理の入口で候補を出す。型を telescope に開き、後続引数の型、結論、抽象化した値で自由変数を追う。局所 instance は探索や elaboration への影響も含めて判断する。 | 最初は一入口あたり数秒〜数十秒の目標。100宣言で測り、候補の再ビルドは別計測。証明の数学的な最小性はレビューする。 |
| 埋められない仮定、未供給の入力、実際に選ばれる instance | 主経路と承認済みの公開入口を対象にする。指定の宇宙、import、open、局所 instance を持つ例で型を正規化し、typeclass 探索の結果と選んだ定数を記録する。構造体の仮定束は field と実際の供給を併せて見る。 | 対象ごとに小さい例を束ねて数十秒〜数分を目標。探索の時間切れは要調査。入力の数学的な妥当性はレビューする。 |
| 主張の展開後の一致・API 適用 | G3/G5 の意図した署名変更の確認に使う。型の保存指紋が違ったとき、指定した transparency と名前写像で definitional equality を調べる。部分、片方向、強い仮定つきの文献対応は照合理由に戻る。 | 対応表の変更行を対象に秒〜分。展開の深さと失敗時の診断を計測し、全宣言への一律の展開は導入判断を保留する。 |
| 型付け・適用例 | 取り込みごとに変更された公開 API について、利用側の import と elaboration を含む小さな例を再ビルドする。全対象のビルドは G1 に置く。 | 入口と依存を共有する例を束ね、塊あたり数十秒〜数分を目標にする。全体の温キャッシュ計測と、版更新の再ビルドは別に集計する。 |
| 安全性・属性・証明手段 | 記録上の `unsafe`、`implemented_by`、extern、partial などの差分に、Lean 上の実際の属性解決を追加する。`native_decide` の公理、不要な `Classical` や weak existence からの choose には実行経路とレビューを使う。 | 変更分の候補だけを対象とし、秒〜分を目標。除去した代替証明の対象ビルドは別計測。 |
| import の除去、オプション、引用登録 | import グラフ、スコープ付きのオプション、コメントと引用項目の照合は記録・ソース側に置く。import を除去した変更は記法と推論を含む利用側のビルドで、引用登録の変更は対象を import した環境の `@[cite]` で確かめる。 | 記録・ソースの照合と Lean の環境構築を別に計測する。変更したオプションは対象ビルドの診断と時間を採り、引用登録は同じ import 閉包ごとに束ねて数十秒〜数分を初期枠とする。 |
| カーネル再検査（lean4checker 相当） | 版更新の別枠の候補。import 後に既存の定数を見るだけでなく、依存順に宣言を核へ入れ直し型と値を検査する。Mathlib/Lean のパッケージ由来の台と本体根を区切り、帰納群、unsafe、opaque、IR の扱いを先に小規模で検証する。 | 今の段では未計測。公開・private・巨大な証明の代表を各100件と選び、値サイズ帯別の秒数を採る。360,168件の総計はその結果から見積もる。初期の計画枠は数十分〜数時間とし、通常の取り込みには入れない。 |

`collectAxioms` は import 済みの公開宣言について Lean 自身の保存した公理拡張を参照する。そのため段3の比較で検出できるのは、主に採取器の解釈・被覆・所有元の差。値からの独立な再訪問を検証する場合は、保存拡張を使わない照合器を少数の宣言で検証し、純粋な核再検査とは別に計測する。

## 2. 記録監査と共有する情報

- 共有するのは基準コミット、ツールチェーン・パッケージの版、例外の正本、結果を結合する所有元とカーネル名。二者の入力の一致を実行の最初に確かめる。
- 母集団は、記録側で Git の追跡リスト、再計算側で実際に import したモジュールの定数表を列挙する。再計算側の目標はクリーンな作業木で Lake のパッケージ設定とソース探索から別に生成する。記録側が出力した宣言名を絞り込み条件に使わない。両方の出力を独立に build 対象リストと照合する。各モジュールの件数、ゼロ件のモジュール、名前と所有元の重複を検査する。
- 記録側は成果物のレコードと保存拡張を直接解読し、再計算側は Lean の import と組み込み関数を使う。比較器は等しい名前の集合と判定を照合し、未判定・余分・足りないを別々に扱う。判定規則のコードを共有すると規則のバグを共通に拾うため、許可外の公理、第三の直接 sorry、型側だけの禁止依存、モジュール欠落、同名別所有元を使う負例を両方に通す。
- 同じツールチェーンの成果物を入力にする比較には共通原因が残る。版更新での fixture の新規ビルド、独立な型検査、将来の核再検査は、その残りを狙って行う。

## 3. 塊・依存・資源

対象モジュールを重複なく塊に割り当て、実際の import 閉包には塊をまたぐ依存も含める。集計は割り当てた所有元だけを書き出し、依存先の結果を他塊の対象判定の代わりに使わない。同じカーネル名を複数の独立モジュールが持つ場合、各所有元の実体を Lean に渡して照合し、由来を記録する。

計画にはモジュール数に加えて外部パッケージの閉包を入れる。モジュールあたり3〜4ファイルを目安にし、`kern.maxvnodes`、`kern.maxfiles` の現時点の余裕と最大 RSS を採る。全体 import の読み手はこのレーンで1本とし、広い塊は他の大きな読み込みがない枠を使う。足りないときは葉を同じ依存群に寄せて塊を再分割する。ファイル上限の診断は環境試行に記録し、同じコミット・塊を競合のない枠でやり直す。総時間は各塊の和と鍵待ちを分ける。核再検査の塊は相互再帰・帰納群を途中で分けない。

段3の全公理比較は7塊で、外部依存を含む閉包は1塊あたり17,980〜23,000モジュールだった。Lean の実行は合計667秒、最大 RSS は塊ごとに5.44〜6.74 GiB。通常の計画では閉包18,500本（約55,500〜74,000ファイル）を切り分けの目安とし、23,000本の塊は実行直前の余裕で判断する。環境依存の検査は入口を単位にして同じ閉包内の例をまとめ、段3で測った環境構築時間と、別途測る検査本体の時間を足して枠を決める。

## 4. 実行頻度

取り込みごとに G1、記録監査、変更モジュールと影響する公開入口の小さな Lean 検査を回す。全公理の再計算は Lean/Mathlib の版更新時と、通常は週1回を初期案とする。時間・発見率・夜間枠を4回分記録して間隔を見直す。版更新の最初に正例と負例の自己試験を通し、全再計算を終えてから新形式の記録監査を正式に扱う。核の再検査は試作が済んでから、版更新・公開前のどちらで回すか決める。

## 5. 食い違ったとき

比較を不合格とし、記録監査の合格を使う取り込みを止める。旧監査は継続する。コミット、ツールチェーン、成果物のハッシュ、閉包、所有元付きの差分を固定して保存する。小さい塊で再実行し、欠損・古い成果物・拡張形式・名前の衝突・規則差の順に調べる。環境上限なら同じ試行を競合なしでやり直す。公理の値や許可が本当に変わった場合は、理由と承認を記録して基準を更新する。復帰の条件は負例が落ち、修正した塊と全体の比較で未説明差が0になること。

## 6. 旧領域監査76本との関係

全公理の再計算は、76本が使う Lean の公理取得を全宣言について覆う。76本の対象選択と許可集合は記録監査の領域規則にも持ち、旧判定と所有元・名前・結果を照合できるようにする。厳格な sorry、期待する所有元と宣言種別、型・値の禁止グラフ、import 境界は、表に十分な証拠があるものから記録監査へ移す。指定型への適用、実際の instance 探索、展開する型の照合、ソース上の登録は専用の Lean/ソース検査に残す。新旧を並べて走らせ、指定した違反をそれぞれ検出することを確かめてから、旧スクリプトごとの廃止を承認する。
