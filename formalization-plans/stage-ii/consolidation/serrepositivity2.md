# SerrePositivity2：新しいプロジェクトの決定の記録

2026-11-21 開始。場所は隣の `SerrePositivity2`（git は手元のみ）。経緯は [enrichment-w1.md](enrichment-w1.md) の決定 10 と [cleanup-log.md](cleanup-log.md) §26。プロジェクトの規則は、その README が正。ここには、決定とその理由を足していく。

## 決定 1：Mathlib だけに乗せて、下から作る（ユーザー、11-21）

- 依存は Mathlib とそのプロジェクトのファイルだけ。旧い側を import しない。旧いコードは参照しながら書く。
- 持ってくるファイルは、必要になった時に、ファイルごとに「写す／要る分だけ新しく書く／書き直す」を決める。一番下の層は、基準に届かないものを写さない。
- 下の層は、上を積む前にユーザーが読んで固める。
- 未決：段 3e の後に何を積むか（第一候補は対称スペクトルの豊穣化）。全体を新しい側に移すか、旧い側とつなぐか。

## 決定 2：文献の印を最初から強制する（ユーザー、11-21）

- 公開の宣言は、文献の番号（`@[cite KEY "番号"]`）か、補助の印（どの宣言のための補助か）のどちらかを持つ。どちらも無いものが 1 件でもあれば、検査は失敗。自動で作られる宣言は、元の宣言の印を引き継ぐ。
- 書く前に対応表を作る：扱う節の項目を全部挙げ、「形式化する／Mathlib にある（名前）／今回は扱わない（理由）／後で」に分ける。
- 主張は原文と並べ、違い（仮定、向き、合成の順）を記録する。番号は `~/serre-evidence/references/` の本文で確かめる。本文が無い文献は、ユーザーに頼む。
- Mathlib にあるものは書き直さず、Mathlib の宣言を使う。
- 補助の印の乱用を防ぐ：補助の割合を数字で出し、読み直しで調整役が一つずつ確かめる。

## 決定 3：状況と計画は Verso Blueprint で。コードから生成する（ユーザー、11-21。まず試す）

- 旧い側の `blueprint/` と同じ仕組み（`leanprover/verso-blueprint`）を使う。leanblueprint（LaTeX）と doc-gen4 は使わない。Mathlib の分の文書は作らない。
- **書かれたコードの状況は、全部自動で集める。** 生成器が、文献の印（`@[cite …]`）、補助の印、docstring、型、記録監査（`sorry`・公理・依存）から、ページを作る。文献の項目ごとに、対応する宣言と、その下の補助の宣言を並べる。人はページを書かない。
- **これからやることだけ、予定の表に書く**（文献の番号、主張を言葉で、予定の名前、依存）。その番号の文献の印を持つ宣言がコードに現れたら、自動で書かれた項目に置き換わる。型の一覧と対応表の置き場所が、これになる。
- 章の冒頭の説明（全体の筋）は、要る所だけ短く手で足せるようにする。数学の読み物の書き場所も、これに決める（保留を解く）。
- 見た目は旧い側の `style/`（11-18 承認）を引き継ぐ。
- 試しの範囲は豊穣化の一般論：段 3a′ はコードから、段 3b〜3e は予定の表から。確かめる点は、これからやる項目の表示、全宣言を載せた時の読みやすさ、作り直しの時間。結果をユーザーに見せて、続けるかを決める。
- 作るのは ⑦（LI-W1 段 1 の報告の後）。⑧ の作業木とぶつからないよう、別の作業木で行う。読んだかどうかの台帳は調整役が記録する。

## 決定 4：検査と枝（ユーザー、11-21。基本は了承。時間をかけないことが条件）

- **枝**：レーンは枝で作業する。main に入るのは、読み直しが済んで合格したものだけ（調整役が取り込む）。main にあるもの＝固めたもの。
- **取り込みの時の検査**（調整役）：全体のビルド（標準の linter と `#lint` が警告 0）、公理は Lean の標準の三つだけ、`sorry` 0、文献の印（印の無い公開の宣言が 0、補助の割合を記録）、前後の比較（固めた層の宣言の名前・型・公理が不変）、避ける書き方の数え上げ、blueprint の作り直し（リンクの切れ 0）。旧い側の監査のスクリプトは持ってこない。
- **固めた層**：合格して main に入ったファイルは、ユーザーの承認なしに変えない。変えたい時は止まって報告し、上に積んだものの建て直しの範囲を先に数える。
- **`sorry` と公理**：main は最初から `sorry` 0、公理は標準の三つだけ。未証明の入力に依存する所（BS の引用など）まで積む段階で、扱いをあらためて決める。
- **写したファイル**：旧い側の同じ名前の宣言と、型・公理が同じことを機械で確かめる。書き直したファイルは、型が変わった宣言の一覧を出す。
- **証拠を溜めない（ユーザー、11-21：追跡されないファイルが溜まるのは避ける）。** 検査のログは保存しない（検査は数分で、そのコミットでやり直せば同じ結果が出る。一時の場所に出して、終わったら消す）。残すのは、取り込みごとの結果の一行だけ（コミット、日付、合否、時間、宣言の数・`sorry`・文献の印の数）で、git の中の小さな表に足す。レーンの報告は、レーンごとに一つのファイル（`docs/report-<レーン>.md`）に書き、段ごとに前の内容を消して書き直す（11-21 に改めた。最後のメッセージに全部書かせると伝達が大変で、表も崩れる）。段ごとのファイルは作らない。古い報告は git の履歴に残る。最後のメッセージは数行（枝とコミット、止まった理由、報告の場所）。レーンを閉じる時にファイルを消し、残すべき判断はその前に調整役が決定の記録に写す。git の外に置くのは、配布できない文献（`~/serre-evidence/references/`）だけ。
- 手で書く文書は、規則（README）と決定の記録（`docs/decisions.md`）、それに動いているレーンの数だけの報告（上書き）にする。文献との対応、これからやること、数学の説明は blueprint。型の一覧や設計の下書きは blueprint の予定の表。`docs/citation-plan-enrichment.md` と `reference/stage3a/` は、blueprint が同じ内容を出すこと・段 3a′ の合格を確かめた時に消す。
- 旧い側の `~/serre-evidence/`（11-21 時点で 63 GB、約 7 万ファイル）は、⑦ の区切りの時に「この先も使うもの」を挙げさせ、それ以外を消す対象としてユーザーに見せる（消すのは承認の後）。

### 時間をかけない（ユーザー：監査やビルドに時間がかかって作業が進まないことは避ける）

- **検査の時間は、変更の大きさに比例させる。プロジェクトの大きさに比例させない。** ビルドは変えたファイルとその下流だけ（下から積み、下の層を変えなければ、新しいファイルだけになる）。記録監査は、モジュールごとに結果を保存し、変わったモジュールだけを読み直す形にする（道具への要求）。
- **目安：取り込みの検査は 10 分以内。** 取り込みごとに時間を記録する。超えたら、予定をずらすのではなく、道具を直す。
- レーンが建てるのは、自分が変えたファイルだけ。全体を読む検査はレーンにさせない。
- 全体をゼロから建て直す検査は置かない（成果物の共有の置き場を使う）。

## 決定 5：複数の実装レーンを並べられる形にしておく（ユーザー、11-21。当面は一本で様子を見る）

並べる時に困らないよう、最初から次の形にする。

- **レーンごとに、持ち場のディレクトリを決める。** レーンが import してよいのは、main（固めたもの）と自分の新しいファイルだけ。ほかのレーンの作業中のファイルを import しない。こうすると、取り込みはぶつからず、どの順で入れてもよい。
- **レーンごとに作業木と枝。** 下の層と Mathlib の成果物は共有の置き場から取り出すので、作業木を増やしても建て直しは起きない。
- **みんなが触るファイルを作らない。** root の import の一覧（`SerrePositivity2.lean`）は、ファイルの一覧から機械で作る（レーンは編集しない）。blueprint も生成物。予定の表は領域ごとのファイルに分ける。
- **固めた層に足したいものは、新しいファイルに置く。** 二つのレーンが同じ補助を別々に書いた場合は、取り込みの時に調整役が一つにする（同じ文献の番号を持つ宣言が二つあれば、文献の印の検査で分かる）。
- **割り当ては、旧い側の import の関係から決める。** Mathlib だけに依存するモジュール、その上のモジュール、…と層に分け、互いに依存しないかたまりを別々のレーンに渡す。この地図は、並べる前に作る（Lean を変えない作業）。
- **並べた時に詰まるのは、読み直し。** 実装が並んでも、読む人は増えない。並べる前に、何をユーザーが読み、何を機械の検査と調整役・別のエージェントの読み直しで済ませるかを決める（未決。たとえば、土台の一般論は全部読む、そのまま写したファイルは機械の一致の検査だけ、など）。

## 決定 6：docstring は Mathlib の基準で、式を入れて書く（ユーザー、11-21。見本を見て了承）

旧い側の規約（概要・方針・規約・使われ方、10 月）は使わない。基準は Mathlib の Documentation style（<https://mathlib.org/contribute/doc.html>）。違いは、日本語で書くことだけ。

**宣言**
- 一文目に、**何であるか**を式つきで書く。定義なら、どの対象・どの射か（例：「評価 `ev : X ⊙ᵣ Map(X, Y) ⟶ Y`。随伴 `X ⊙ᵣ - ⊣ Map(X, -)` の余単位。」）。定理・補題なら、主張の等式や同型そのもの。
- 数学的な意味を書く。どう実装したかを一文目にしない（Mathlib：「docstring は定義の数学的な意味を伝える」）。
- 続けて、要る場合だけ：作り方（一〜二文）、文献の式との違い（向き、因子の順、仮定）。
- 言葉は文献のもの（写像対象、テンソル、余テンソル、評価、転置）に限る。独自の言葉（原対象、終対象、係数、点）を使わない。
- 補題にも式を一つ書く。一行で足りるものは一行。構造とクラスの欄にも一つずつ付ける。完全な文は句点で終える。

**ファイルの冒頭**
- 題（`#`）、要約（主な主張を式で）。続けて、要る節だけを、この順で：`## 主な定義`、`## 主な結果`、`## 記法`、`## 実装上の注意`、`## 文献`。
- 「使われ方」は置かない（使う側が変わるたびにずれる）。経緯を書かない。
- ファイルの中の区切りは `/-! ### … -/`。

**式**
- Unicode の式をバッククォートで囲むのを基本にする（`Hom(X ⊙ᵣ P, Y) ≃ Hom(P, Map(X, Y))`）。エディタでそのまま読めることを優先する。図式や長い式で要る時だけ LaTeX（`$…$`、`$$…$$`）。
- Lean の名前と式はバッククォート。説明のための記号（`Map(X, Y)`、`Y ^ P` など）は、ファイルの `## 記法` の節で決め、Lean の名前との対応を書く。

見本（`ClosedModule`、`ev`、`comp`、`hom_ext`、ファイルの冒頭）は、11-21 の調整役とのやり取りで示したもの。段 3a′ の読み直しの時に、全部の docstring をこの書き方に直す。

## 決定 7：全部を blueprint で把握する（ユーザー、11-21）

- blueprint を、このプロジェクトの唯一の文書にする。載せるもの：いまの状況（コードから自動）、文献との対応（文献の印から自動）、数学の説明（docstring から自動、章の筋だけ手書き）、これからやること（予定の表）、ユーザーが読んだかどうか、読み直しで見つけた点と決めること（調整役が書く小さなデータ）、決定とその理由（手書きの章）。
- blueprint ができたら置かないもの：手引きのページ（Artifact）、文献の対応表、型の一覧、この決定の記録の紙。外に残るのは、README（書く人のための規則）と、レーンの報告（一レーン一ファイル、上書き）だけ。
- 仕組みが無いと何も見えなくなるので、順番を変える：⑦ は LI-W1 段 1 をいまの状態で区切り、すぐ blueprint の試しに入る。段 3b に進む前に、最初の版を作る。それまでは、読み直しの結果は調整役がその場で伝える。
- この紙（serrepositivity2.md）は、blueprint の「決定」の章に移した時点で、正を譲る。

## 決定 8：コードの基準は Mathlib の公式の手引き（ユーザー、11-21）

docstring だけでなく、コードも Mathlib の基準に照らす。書く時にも、確かめる時にも適用する。

**基準（正本は公式のページ）**

- 書き方：<https://mathlib.org/contribute/style.html>
- 名前：<https://mathlib.org/contribute/naming.html>
- 文書：<https://mathlib.org/contribute/doc.html>
- 査読の観点：<https://mathlib.org/contribute/pr-review.html>

このプロジェクトでの違いは三つだけ：docstring は日本語、著作権のヘッダは付けない、文献は `@[cite …]` で引く（`references.bib` ではなく）。旧い側の `new-code-quality.md`（17 項目）は、公式の手引きを私がまとめ直したもので、以後は公式の手引きを正とし、食い違えば公式に従う。プロジェクト固有の規則（文献の印、作り方が複数ある構造を instance にしない、など）は README に置く。

**書く時（レーン）**

- README に上の四つを基準として書き、指示のたびに繰り返さない。
- 手引きから、間違えやすい点を README に抜き出す：
  - 一行 100 文字。`by` は行末。`fun x ↦`。`<|`（`$` は使わない）。構造と instance は `where`。空行を宣言の中に置かない。
  - 仮定は、証明の最初で導入するならコロンの左に。引数と戻り値の型を全部書く。`Type*`。
  - 最後の `simp` は絞らない（`simp only` に書き換えない）。途中の `simp` は絞る。
  - `simp` や `rw` の後に `erw` や `rfl` が要るのは、API の補題が足りない印。補題を足す。
  - `def` は既定のまま（`abbrev` や `irreducible` にするなら理由を書く）。
  - 名前：定理は `snake_case`、型と Prop は `UpperCamelCase`、その他の項は `lowerCamelCase`。主張から名前を作る（記号の辞書、仮定は `_of_`、`_apply`・`map_`・`ext`・`_injective`・`_inj`、`left`/`right`）。名前空間つきの定義を補題の名前で引く時は名前空間を落とす。
  - 新しい定義には補題を付ける（`@[simps]` で足りればそれで）。`@[simp]`・`@[ext]`・`@[reassoc]` を適切に。定義を開かずに書き換えられる補題を用意する。
  - import を広げない。ファイルは 1000 行を超えたら分ける（このプロジェクトの目安は 500 行）。

**確かめる時**

- 機械：Mathlib の標準の linter（`lakefile.toml` で有効）、`#lint`、Mathlib の書式の検査（`lint-style` に当たるものをこのプロジェクトのファイルに当てられるかを確かめる）、import の過不足の検査。警告 0 が取り込みの条件。
- 別のエージェントの読み直し：公式の査読の観点を、そのまま確認の表として渡す。項目は、書式、文書、置き場所、重複（Mathlib に同じものが無いか）、改善（証明を補題に分ける、より適切な tactic、定義の形式化が最良か）、API（属性、定義を開かない書き換えの補題、構成子）、一般性（文献のより一般の形）、設計（Mathlib の既存の型・クラスとの整合、instance のひし形を作らない）。結果は、項目ごとに「問題なし／指摘」で返させる。
- 調整役の読み直し：文献との対応と数学。上の表で「指摘」になった項目の要否を判断する。
- 結果は、blueprint の項目ごとの覚え書きに載せる（仕組みができるまでは、その場で伝える）。

## 決定 9：`@[simps]` と手書きの補題の使い分け（調整役、11-21。ユーザーの問いを受けて）

- 構造の欄をそのまま取り出すだけの補題（閉じた加群の欄、随伴の欄など）は、`@[simps]` で作る。
- 使う側が Mathlib の `def` を通して書くもの（豊穣圏の Hom・`eId`・`eComp`・`eHomEquiv`・`eHomWhiskerLeft`・`eHomWhiskerRight`）は、手で書く。これらは Mathlib で普通の `def` なので、`@[simps]` の作る補題の左辺（構造の欄を取り出した形）が、使う側の書き方に当たらない。Mathlib の自己豊穣化（`enrichedCategorySelf_hom`・`_id`・`_comp`）と同じ形にする。
- 同型の成分が恒等射である補題は、手で書き、`@[reassoc (attr := simp)]` を付ける。

## 決定 10：豊穣圏は写像対象の随伴だけから作る。クラスを二段に分ける（ユーザー、11-21）

- 豊穣圏の構成（評価、合成、単位律、結合律、Hom の比較）は、写像対象の随伴しか使わない。余テンソルは使わない。要らない仮定を残さない。
- クラスを二段にする：写像対象の随伴だけを持つ段（豊穣圏はここから作る。Riehl Definition 3.7.2、Lemma 3.7.7、Remark 3.7.9）と、余テンソルの随伴を加えた段（閉じた加群。Definition 3.7.3、10.1.3、Proposition 10.1.4）。文献もテンソルつきと余テンソルつきを分けて定義している。
- 自己作用の豊穣圏は組紐なしで作り、Mathlib の自己豊穣化と一致することを示す。組紐が要るのは、余テンソルの随伴だけ。
- 基底の取り替えの補題と Hom の比較は、Mathlib の型の別名 `TransportEnrichment G M` の上で述べる。
- 文献の印の道具（`Util/`）は、検査と blueprint の対象から外す。Mathlib に足りないものを補った宣言は、親を Mathlib の宣言にした補助の印で表し、blueprint では「Mathlib の補い」の章に出す。

## 決定 11：⑦ を閉じ、blueprint の道具は調整役が持つ（ユーザー、11-21）

- 監査のレーン ⑦ は、LI-W1 段 1 と blueprint の試作で閉じた。旧い側の作業木と枝は全部消した（main に取り込み済み）。
- blueprint の生成の道具と中身（章の説明、予定の表、読み直しの覚え書き、決定の章）は、調整役が直接直す。別の作業木 `SerrePositivity2-blueprint`（枝 `blueprint-w1`）。

## 決定 13：目標と、そこへの作り方（ユーザー、11-21）

- **最終の目標**は、主定理が標準の公理だけに依存すること（`sorry` 0）。残っている未証明の入力は三つで、要るものは二つ：∞ 代数（BS の引用を証明に置き換える。最初の目標は P⁰、DAG XIII 2.2.6）と、K 理論（論文の定理 3.1 と補題 4.6 の降下）。
- **K 理論の側の目標は、Blumberg–Gepner–Tabuada（BGT）の必要な定理。** まず、道が要る BGT の定義と定理を見つけて、それを目標に据える。
- **作り方は ∞ 圏を土台にする。モデル圏はできるだけ避ける。** K 理論の文献（BGT、Land–Tamme）はもともと ∞ 圏の言葉で書かれている。旧い側が dg 圏やスペクトルの模型を使ったのは、∞ 圏の土台を避けて先に進むための選択だった。∞ 圏を土台にすれば、対称スペクトル、Ω スペクトル、レベルモデル構造、dg の上の S 構成、hammock 局所化は要らなくなる。残るのは、単体的圏と単体的神経（∞ 圏への入口）、dg 神経（環の導来圏を ∞ 圏として作る入口）。
- 土台の文献は、モデル圏を使わずに展開している Kerodon を第一にする。HTT・HA の主張を使う所は、モデル圏なしの証明があるかを項目ごとに本文で確かめる。
- **進め方**：調整役が「目標と道」をまとめ、blueprint の最初の章に置く。中身は、定義の列、目標から逆にたどった定理の列（文献の番号）、各項目のモデル圏への依存、旧い側から使えるもの。これができてから、豊穣化の次に何をやるかを決める。
- 豊穣化の一般論の使い道は、スペクトルではなく、単体的圏と dg 圏になる。対称スペクトルは道の上に無い（練習の題材にするかは、道の紙ができてから決める）。
- レーンは増やさない。主定理の証明済みの部分（991 モジュール）は、最後に持ってくる。
