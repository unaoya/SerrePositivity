## 0. 目標と、IC-2 との関係

整理の目標（ユーザー、11-19）は次の三つ。

1. 全てのファイルの内容をブループリントで捕捉する。
2. その上で、内容に合わせたディレクトリ構成とファイルの分割に基づいて配置する。
3. 文献の形式化がどこまで進んだかを確認できる。

検討の単位は**ファイルではなく宣言**とする（ユーザー）。ファイルは細かく割れすぎている（11-19 の実測、Archive を除く：34,336 本・163,207 宣言・312 万行、1 ファイルの宣言の中央値 3・行の中央値 72、宣言 3 個以下が 17,542 本）。補助のファイルを減らすのも整理の目的に入る。

ブループリントは二つにする（ユーザー承認）：
- **文献のブループリント**（今のもの、`blueprint/`）：文献の項目ごとの主張・状態・結んだ宣言。進み具合を見る。
- **把握のブループリント**（新しく作る）：本体の側から見る。節点は宣言の**まとまり**（文献の項目の補助、または本体の構成の主題）で、宣言は節点の中の表にする。

**進め方の順序**（ユーザー、11-19）：全宣言を把握する → 内容ごとに整理する → 重複などをまとめる → ファイルを決める → ディレクトリ構成を決める。ディレクトリは最後に決め、前の段の結果から導く。

**整理の規則の決定**（ユーザー、11-19 午後）：
- 順序：把握 → 概念の整理（概念のブループリントは全ての宣言を必ず覆う）→ 補題・証明の簡略化と重複の統合、Mathlib への置き換え → ファイル・ディレクトリ → 文献のブループリント（二段目：文献の形式化の度合いの確認）→ 残りの計画。
- **文献にある定義・定理・補題そのものは変えない**。その準備として作った宣言は、主張も証明も変えてよい（最終的に証明が正しく通ること）。整理のために Lean のコードを書くこと（証明の短縮、重複の統合、一般の補題への置き換え）は「新しい形式化」に当たらず、許される。
- Mathlib にあるものは Mathlib に置き換え、Mathlib に準拠した形にする。Mathlib に送る価値のあるものは記録する（送るかどうかは別）。
- 目指す状態：人が読めるように整理され、ファイル数・行数が少なく、分野の専門家が把握しやすい。行数を減らすことがベンチマークの一つ。「把握しやすいか」の判定はユーザー。ディレクトリの木は Mathlib の構造を参考にし、ファイルは一つのまとまりで docstring から中身が分かり、概念のブループリントの目次とディレクトリが対応する。
- **見直しの後の決定**（ユーザー、11-19 夕）：
  - 固定する宣言は、対応表が名指しする宣言の全部（状態が「一部」のものも含む）。まずは変えないで進め、後で改めるかもしれない。整理は何回か繰り返してよい。
  - 検査（保存比較）と監査は、整理した後に見直す。最近の配置（Kerodon に合わせた配置、IC-1）と向きが逆になることは気にしない。名前空間は後で考える。文献のブループリントと対応表の追従も後で。
  - Mathlib は固定版のまま。
  - 一回で全部うまくいかなくてよい。機械的に全部できなくてよい。やりながら直す。CD-W1（概念の辞書と木）は、この指示書の 1（宣言の表）が出てから ⑧ が始める。**1・1′・1″ ができた所で一度コミットして短く報告し、止まらずに 2 以降へ進む**（⑧ が表を使い始められるように）。
- この段 0（DI-W1）自体は紙と書き出しだけで、Lean のソースは変えない（下の §1 のまま）。上の規則は適用の段のもの。

**IC-2 は止める**（ユーザー承認）。今の組をコミットして止まる。残りの組への一括の承認は取り下げる。IC-2〜5 と BS の整理は、この目録の上で「まとめ直し＋移動」の束に組み直す（同じ宣言を二度動かさないため）。IC-2 の段 0 の資料（`research/infinity-consolidation-w2/`）は捨てずに、組み直しの入力にする。

3. **根**：(i) 論文の主定理と sorry の閉包の対象、(ii) 対応表（`research/*-coverage` のすべての review と items）が名指しする宣言と、その項目・状態、(iii) 全監査の期待の一覧。根ごとに件数。
