# 新しく書く一般論のコードの品質：基準と確かめ方

2026-11-21。ユーザーの方針：整理の中で新しく書く形式化（最初は豊穣化の一般論、EN-W1 段 3）は、コード自体の質を十分に高くし、それをきちんと確かめる。

この紙は、新しく書く一般論（`CategoryTheory/` の下に置くもの）に適用する。既存のコードの整理には [cleanup-rules.md](cleanup-rules.md) を適用する。

## 1. 基準

目標は、**そのまま Mathlib に出せる質**（出す作業は今回はしない）。docstring だけは本体の規約（日本語）に従う。

### 主張（定義と定理の形）

1. **文献どおり。** 各宣言は、対応する文献の番号を `@[cite …]` で持つ。docstring に主張を言葉で書き、文献と書き方が違う所（合成の順、作用の向き、仮定）を断る。文献に相手の無い補助は、何のための補助かを書く。
2. **仮定は要る分だけ。** 型クラスの仮定は、その宣言の主張と証明が使うものだけにする（`SymmetricCategory` が要らない所で要求しない、`MonoidalClosed` が要らない所で要求しない）。文献より弱い仮定で示せるなら弱くし、その旨を書く。使っていない仮定は、監査の検査（AR-W1 段 7）にかける。
3. **宇宙は一般に。** 対象と射の宇宙を、型ごとに独立の変数にする。固定するときは理由を書く。
4. **定義は、中身が読める形で。** 同型は `Iso` を返す定義として作り、存在の主張（`∃`、`Nonempty`）にしない。構造の欄を `by` の中の長い手続きで埋めない（中身が式として読めるようにする）。必要なら補助の定義に分ける。
5. **等式で型を移さない。** 関手や対象の等式（`eqToHom`、`eqToIso`、`▸`、`cast`）で主張をつなぐ形にしない。自然同型でつなぐ。等式が要るのは、定義から等しいことが `rfl` で示せる場合だけ。
6. **構造を増やさない。** Mathlib に同じ概念があればそれを使う。Mathlib の概念では足りずに本体に定義を足すときは、docstring に「Mathlib の何と、どこが違うか」を書く。

### 使い勝手（API）

7. **定義には、その定義を使うための補題を付ける。** 構造を作る定義には、各欄を取り出す等式（`@[simps]` で足りるならそれで。足りなければ名前を付けて）。同型には `hom`・`inv` の成分の式。射の等式には、合成の続きに当てられる形（`@[reassoc]`）。
8. **`simp` の向き。** `@[simp]` を付ける補題は、右辺が左辺より簡単になる向きだけ。`simp` の正規形（Mathlib の作法）に合わせる。付けない場合は理由が分かるようにする。
9a. **クラスか構造かは、Mathlib の同じ形の概念に合わせる。** その型に付く構造（作用、閉であること、豊穣化）はクラス。関手や随伴のように値として渡すものは構造。Mathlib でクラスであるものを、構造の欄に包まない（欄の型の中で `letI` が要る形は、設計が合っていない印）。
9. **instance は慎重に。** 一般論の中で、全体の instance として登録するのは、その型にその種類の構造が一つしか無いものだけ（LI-W1 の規則）。作り方が複数ある構造（作用から作った豊穣化と、基底を取り替えた豊穣化）は、定義にして、使う側が選ぶ。`letI`・`haveI` で主張の中に instance を差し込む形は、主張が読みにくくなるので、束ねた引数で渡す形を先に検討する。
10. **名前は Mathlib の作法。** `CategoryTheory` の名前空間の下。定理は主張から名前が決まる形（`foo_comp`、`foo_hom_app`）。経緯に由来する名前（`…Local1`、`legacy…`、`native…`）を付けない。

### 証明

11. **短く、筋が読める。** 一つの証明は 30 行を目安にする。超えるなら、数学的に意味のある補題に分ける（「補題 A の前半」のような分け方をしない）。文献の証明の段（全単射の列の一段、図式の一つの可換性）が、補題の単位になるようにする。
12. **使わないもの。** `sorry`、新しい公理、`set_option maxHeartbeats`・`synthInstance.maxHeartbeats` の引き上げ、`set_option backward.*`、`erw`、`native_decide`、`decide` での重い計算、`unsafe`、`open Classical`（要るなら理由つきで局所に）。
13. **避けるもの（使うなら理由を一行）。** `change` と `show` で型を書き直すこと（定義を開く補題が足りない印）、`simp` を引数なしで途中に使うこと（`simp only [...]` か、最後の一手だけ）、`rfl` に頼った長い計算（定義が変わると壊れる）、`convert`・`congr` の深さ指定、`aesop_cat` に任せきりの欄（何が示されたか読めない場合）。
14. **遅くしない。** 一つの宣言の検査が数秒を超えるものを一覧にし、原因（instance の探索、定義の展開）を調べる。ファイルの建つ時間を記録する。

### ファイル

15. **一つのファイルは一つの主題。** 決定 5 の分け方。冒頭の説明（概要・方針・規約・使われ方）は本体の規約どおり。ただし「旧モジュールから移した」のような経緯は書かない（履歴は Git にある）。
16. **import は要る分だけ。** `Mathlib` 全体を import しない。使っていない import を残さない。
17. **1 ファイル 500 行を目安。** 超えるなら主題で分ける。

## 2. 確かめ方

三つを重ねる。一つ目は書いた本人、二つ目は機械、三つ目は別の目。

### (ア) 書いたレーンの自己点検（段ごと）

報告に、次の表を付ける。

- 宣言ごと：名前、種類、行数、文献の番号、検査の時間、使っている仮定。
- 上の「使わないもの」「避けるもの」の出現箇所（ファイルと行）と理由。0 件なら 0 件と書く。
- 30 行を超える証明の一覧と、分けなかった理由。
- 型の一覧（`stage2-types.md`）との違い。

### (イ) 機械の検査

- Mathlib の標準の linter（`lakefile.toml` で有効）が警告 0。警告を消すための `set_option linter.… false` を足さない。
- Batteries の `#lint`（未使用の引数、`simp` の正規形、docstring の有無、instance の優先度など）を、新しいファイルにかけて 0 件。
- 記録監査（`scripts/audit2`）：公理、sorry、使われていない仮定（段 7 の検査ができていれば）。
- 調整役の数え上げ：新しいファイルの `set_option`・`erw`・`change`・`show`・`eqToHom`・`letI`・`haveI`・引数なしの `simp` の件数、証明の行数の分布、ファイルの建つ時間。

### (ウ) 別の目による読み直し

- **調整役**が、新しい宣言を全部、型の一覧と文献の本文に照らして読む。見るのは、主張が文献どおりか、仮定が過不足ないか、定義の中身が読めるか、補題の単位が数学の単位になっているか。
- **書いたレーンとは別のエージェント**に、設計の経緯を渡さずにコードだけを読ませる（Mathlib の査読のつもりで）。指摘を一覧にし、調整役が要否を判断する。
- 指摘は、直す／直さない（理由）を記録し、直すものは次の段の最初に直させる。

### (エ) ユーザーによる読み直し

ユーザー自身が、新しく書いたコードを読む（11-21 の決定）。そのために、**一段ごとに止まる**。調整役は、(ア)〜(ウ) の結果をまとめた手引きを渡す：読む順番とファイル・行、宣言ごとの数学の主張・文献の番号と式・Lean の主張・証明の筋、見つかった点、後から変えにくい所（定義の選び方、仮定、名前）。

### 進め方

- 一段を書く → (ア)(イ)(ウ) → 手引き → (エ) → 指摘を直す → main に取り込む → 次の段。
- 読んでいる間、レーンは Lean を変えない下準備（後の段の設計）を進めてよい。
- 段 4 以降（使う側を適用に置き換える）で、一般論の側に補題を足したくなったら、同じ基準と同じ流れで足す。
