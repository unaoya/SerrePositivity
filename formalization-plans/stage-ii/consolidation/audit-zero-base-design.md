# 監査のゼロからの設計（案）

2026-11-20。ユーザーの指示：監査はゼロから設計してよい。AR-W1 段 1 の調査（[report-audit-review.md](report-audit-review.md)、枝 `refactor/audit-review`）を受けた、調整役の案。実施の前にユーザーと相談する。

## 0. 今の仕組みの実態（調査の要点）

- Lean のスクリプトは 423 本・約 20 万行。取り込み時に実行するのは 108 本（延べ 1.44 時間）。実行しない 315 本のうち 163 本は落ちている（110 本は改名に追従していない）。
- 「全体を見る検査」はない。`audit_axioms.lean` は 53 宣言の公理を印字するだけ、`audit_sorries.lean` は主定理の依存閉包（本体 21,792 宣言）だけを見る。許可する公理との照合は領域ごとの監査 76 本がしていて、対象の和集合は 261,830 宣言。本体 360,168 宣言のうち約 9.8 万は、どの監査でも照合されていない。
- root から届かない 4,387 モジュールは、監査が import することでしか建てられていない（2,794 は一本の監査だけ、176 はどこからも届かない）。
- 監査は宣言の名前を手で並べているものが多く、整理のたびに追従が要る（古い名前の削除で 48 本）。

## 0.5 ユーザーの要望（11-20）

設計はこの五つを満たすこと。レビューでは、下の案が各要望をどこまで満たすか、満たさない所は何が足りないかを見る。

| | 要望 | 案の中の対応 | 案に足りないと調整役が考える所 |
|---|---|---|---|
| R1 | コードを書き換えたとき、ブループリントに適切に反映される | G3（対応表の名指しの解決と主張の基準） | ブループリントそのものの生成と、生成物が今のコードと合っていることの検査が案にない。宣言を改名・移動・削除したときに、対応表 → 生成器 → ブループリントの順で自動に追従するか、止まって知らせるか |
| R2 | 文献の内容との整合 | G3 | 「名指しされた宣言がある」ことと「その主張が文献の主張と合っている」ことは別。後者は人（またはエージェント）の照合で、機械の検査が守れるのは「照合した後に主張が変わっていない」ことだけ。照合した時点の主張を基準として残す必要がある |
| R3 | 時間がかからない | §3（25〜30 分の見込み） | 採取の 20 分が大半。差分だけ採取する方法、レーンが手元で速く回せる部分検査 |
| R4 | 全宣言をチェックできる | §2.1・G2 | 自動生成の宣言、private、instance、root から届かないモジュールの扱いを明記する |
| R5 | エラー、不要な仮定、不要な公理、望ましくない方法が紛れていない | G2（公理と sorry）、G4（構造の規則） | 「不要な仮定」（使われていない仮定、埋められない仮定）と「望ましくない方法」（`native_decide`、上限の引き上げ、`unsafe`、`implemented_by`、`sorry` の言い換え、仮定を束ねた未供給の入力の構造体、`Classical` の不要な使用など）の具体的な一覧と、それぞれを表から検査できるか |

## 1. 監査で保証したいこと

何を保証したいかから決める。今の監査がしていることを種類ごとに並べ直すと、次の五つになる。

| | 保証したいこと | 今の担い手 |
|---|---|---|
| G1 | 追跡している全ての Lean ファイルが建つ | root のビルド＋監査の import（偶然に頼っている） |
| G2 | 全ての宣言が、許可した公理だけに依る。sorry に依るのは、許可した未証明の入力を通るものだけ | 領域ごとの監査 76 本（27% は漏れ） |
| G3 | 対応表（`research/*-coverage/`）が名指しする宣言が存在し、主張が変わっていない | blueprint の生成器が解決数を数えるだけ（主張は見ていない） |
| G4 | 決めた構造の規則が守られている（主経路に `[ModelCategory SSet]` のような埋められない仮定がない、層の向き、文献の登録、など） | 個別のスクリプト（Lean と Python） |
| G5 | 整理の前後で、変えていないはずのものが変わっていない | レーンがその都度作る比較（古い名前の削除のとき ⑦ が作った） |

これとは別に、使ってみる例（`example` での適用、具体的な計算）がある。これは保証というより試験なので、G1 に含める（下の §2.6）。

## 2. 設計

### 2.1 中心に置くもの：宣言の表

全ての検査を、**一度の採取で作る宣言の表**への問い合わせにする。

- 採取：全モジュールの全ての定数について、名前・所有モジュール・種類・主張（型）のハッシュ・位置・主張と本体が使う定数・直接使う公理、を出す。概念の木のために作った道具（`research/cleanup-zero-base/dump_all.lean`）がすでにこれを出している（公理は 11-20 に足した）。Lean の起動は 5 回、約 20 分。
- 一つのプロセスで全モジュールを読むと vnode の上限に届くので、root の閉包と残りの塊に分けて読み、名前のハッシュでつなぐ（実装済み）。
- 宣言の名前を手で並べない。対象は「全部」で、例外だけを設定に書く。

同じ表から、概念の木と、整理の数（宣言・行・ファイル）も作る。採取は取り込みごとに一度で済む。

### 2.2 G1：全部が建つ

- 追跡している `.lean`（Archive を除く）の一覧から、全モジュールをビルドの対象にする。監査の import に頼らない。
- root（`SerrePositivity.lean`）から届かないモジュールがあること自体は、別に一覧にして見えるようにする（採取の結果から出る）。届かせるか、Archive に移すかは、整理の中で領域ごとに決める。

### 2.3 G2：公理と sorry

- 表の依存の辺をたどって、全ての宣言について、推移的に依る公理の集合を計算する（Python、数秒）。
- 設定は一つのファイル：許可する公理（`propext`・`Classical.choice`・`Quot.sound`）、許可する未証明の入力（今は主定理の 3 件）。
- 判定：
  - 許可しない公理に依る宣言が 0。
  - `sorryAx` に依る宣言は、全て、許可した未証明の入力を通る。sorry を直接含む宣言は、許可した入力だけ。
  - 主定理が依る未証明の入力が、設定のとおり（今の `audit_sorries.lean` の内容）。
- 報告：`sorryAx` に依る宣言の数を、通っている入力ごとに出す。領域ごとの数も出せる（概念の木と同じ表なので）。
- 本体の外（Mathlib など）の定数は、許可した公理だけに依ると仮定する。この仮定は、参照している外の定数について Lean の `collectAxioms` で一度確かめ、Mathlib を上げるたびに確かめ直す。

### 2.4 G3：対応表

- 対応表の宣言欄の名前を、表の所有元つきの名前に解決する。解決できないもの、複数に当たるものを一覧にする。
- 名指しされた宣言の主張のハッシュを、基準（前回の取り込み）と比べる。変わったものを一覧にする。意図した変更なら基準を更新する（更新はコミットに残る）。
- これで、整理の規則「対応表が名指しする宣言は変えない」を機械で確かめられる。

### 2.5 G4：構造の規則

- 表への問い合わせで書けるもの（ある宣言の集合が、ある定数に依らない。ある名前空間の宣言が、別の名前空間に依らない）は、規則を設定に書いて、G2 と同じ計算で判定する。主定理が旧い入口に届かないこと、主経路に埋められない仮定がないこと、層の向き、がこれに当たる。
- ソースの文字列を見るもの（文献の登録と `@[cite]` の照合、docstring の規則）は、今の Python の検査を残す。

### 2.6 使ってみる例

- 数学として意味のある例（具体的な入力での計算、主要な定理の適用）は、本体の側のファイルに置き、G1 で建てる。建たなくなれば取り込みで気づく。腐らない。
- 「名前を挙げて型を当てるだけ」の例は、G3 に含まれるので要らない。

### 2.7 G5：整理の前後の比較

- 二つのコミットの表を比べる道具を一つ持つ：消えた宣言、増えた宣言、主張が変わった宣言、所有モジュールが変わった宣言。定数の対応表（消した別名 → 行き先、改名）を通して比べられるようにする。
- レーンは整理の一段ごとにこれを実行し、意図しない変化がないことを報告に添える。今はレーンがその都度作っている。

## 3. 取り込みの検証（新しい形）

1. 全モジュールのビルド（G1）。差分だけなので、普段は数分。
2. 採取（約 20 分）。
3. 表への問い合わせ：G2・G3・G4（数秒）。
4. 残した Python の検査。
5. 概念の木と整理の数の更新（同じ表から、数秒）。

今は 51 分（root、監査 108 本、sorry の閉包）。新しい形は 25〜30 分の見込みで、見る範囲は 26 万宣言＋主定理の閉包から、36 万宣言の全部になる。宣言を消す・移す・改名するときに、監査を直す必要がなくなる（例外の設定と、対応表の基準だけ）。

## 4. 今のスクリプトの扱い

| 今のもの | 新しい形での扱い |
|---|---|
| 領域ごとの公理・sorry の監査（76 本） | G2 に置き換える。置き換えの前に、新しい検査の結果が 26 万宣言で今の監査と一致することを確かめる |
| 名前を挙げた `assert_no_sorry` | G2 に含まれる（全宣言を見るので） |
| 印字だけの監査（5 本、42,927 行） | 消す。名指しの存在は G3 |
| 型を当てる例、適用例 | 意味のあるものは本体へ（§2.6）、残りは G3 に含まれるので消す |
| 構造の検査 | G4 の設定へ。ソースを見るものは Python のまま |
| 落ちている 163 本 | 上の分類に従う。大半は G2・G3 に含まれるので消す。意味のある例だけ直して本体へ |
| `scripts/refactor/` の道具（スナップショット、比較） | G5 の道具に一本化する |

削除は、置き換え先が動いて、今の監査と一致することを確かめた後に、一覧をユーザーに見せてから行う。

## 5. 進め方（案）

1. 採取に公理を足す（済み、11-20）。G2 の計算と設定を書く（調整役）。
2. 新しい G2 の結果を、今の領域の監査 76 本と照合する（⑦、AR-W1 段 2）。一致しない宣言は、どちらが正しいかを調べる。今は見ていない 9.8 万宣言の状態を報告する。
3. G1（全モジュールのビルドの対象）、G3（対応表の解決と基準）、G5（前後の比較）を作る。
4. 取り込みの検証を新しい形に切り替える。しばらくは今の監査と並べて実行する。
5. 今のスクリプトを §4 の表に従って片づける（一覧をユーザーに見せてから）。

## 6. 決めておきたいこと

- **許可する未証明の入力の書き方**：今は主定理の 3 件。設定に名前で書く。sorry を直接含んでよい宣言は、これだけにする（今、主定理の閉包の外に sorry があるかどうかは、G2 を動かせば分かる）。
- **root から届かないモジュールの sorry**：届かない範囲にも G2 を同じ基準でかける（案）。止めた経路の部品に sorry があれば、ここで初めて見える。
- **対応表の基準の更新の権限**：対応表が名指しする宣言の主張が変わったとき、基準を更新してよいのは誰か（案：調整役が取り込みのときに、変化の一覧をユーザーに見せてから）。

## 7. レビューを受けた改訂（11-20、AR-W1 段 2、`review-audit-zero-base.md`）

⑦ のレビューの結論：G1 の対象一覧と、新旧の並行計測は始めてよい。旧い監査の置き換えは保留。調整役はこの結論を受け入れ、案を次のように改める（上の §1〜§6 と食い違う所は、ここが優先）。

1. **公理は Lean の判定を基準にする（§2.3 を改める）。** 調整役の計算（依存の辺をたどる）は、Lean の `collectAxioms` と 107 宣言中 15 件で食い違った。原因は、本体の外の定数を値の側で経由する公理を見ていないことと、帰納型からコンストラクタへの辺がないこと。Lean は公理の判定を成果物に保存している（本体 360,168 宣言のうち 295,160）。これを直接読み、保存のない分（private など 65,008）は Lean の `collectAxioms` で埋める。調整役の依存グラフは、経路の説明と領域の規則（G4）に使う。本体の外の定数を「許可済み」と仮定しない。
2. **採取は保存成果物を直接読む（§2.1・§3 を改める）。** import して環境を作るのではなく、モジュールごとの成果物を読む。⑦ の実測では、全定数と instance で延べ 50 秒、公理の保存分で 40 秒（160 モジュールずつ 215 塊、直列）。採取の 20 分は 1〜2 分になる見込み。結合は名前のハッシュだけでなく、名前と所有モジュールで照合する。欠けた節点を空として扱わない。
3. **母集団を先に固定する（§2.2 を強める）。** 本体は 34,250 モジュール・360,168 宣言（def 105,695、thm 251,569、inductive 911、ctor 1,063、rec 911、opaque 19、axiom 0）。追跡しているモジュール、建ったモジュール、採取したモジュール、検査したモジュールの四つの集合を照合し、一致しなければ完了としない。Archive・`scripts/`・blueprint・計画書の中の Lean は本体と別の対象にする。
4. **領域の監査に固有の条件を移す（§4 を改める）。** 公理と sorry の一般の判定だけでは受けきれない条件がある：領域によっては許可した引用への推移的な依存も拒む厳格な sorry 条件（`assert_no_sorry` 27 本・5,133 命令）、型と値で別々の禁止依存（21 本）、期待する宣言の種類・公開範囲・所有元、監査の対象モジュールを実際に訪ねたかの検査（89 本）、禁止入口（主定理から旧 BS 入口 2 件、旧 Kan–Quillen 入口 1 件）、import の境界。これらを G2・G4 の設定に移し、各条件を新しい検査が落とせることを確かめるまで、旧い検査を残す。型を当てる例（319 本・3,774 件）は、安定な API の小さな型の検査と、§2.6 の適用の試験に分ける。
5. **G3 に、文献の照合の基準と、生成物の検査を足す（§2.4 を改める）。** 今の生成器は、改名・移動・削除で名前が解決できなくなるとリンクを黙って外して成功し、同じ名前で主張を変えても気づかない（⑦ が 9 通り試した）。対応表の各項目に、文献の版・項目・対応の種別（全体／部分／片方向／仮定つき）、照合した時点の所有元つきの名前と主張の指紋、照合の理由、確認者を一つの記録として残す。生成の前に全リンクを解決し、生成の後に項目ごとのリンクを期待と比べる。主張が変われば、同じ名前でも再照合に回す。承認した移動で主張が同じなら、所在だけ更新する。
6. **R5 は三段に分ける（§2.5 を改める）。** 禁止（機械で落とす）、候補（機械で警告を出す）、人が照合する、の三つ。使われていない仮定は、宣言の表からは分からず、Lean の中で調べる必要がある。埋められない仮定は、具体的な台（`[ModelCategory SSet]` など）と、一般の変数の上の正当な仮定を区別する。`unsafe`・`implemented_by`・`extern`、上限の引き上げ、警告の抑制は、基準との差分で新しく足されたものを一覧にする。規則の表はレビューの §4。
7. **G5 は主張だけでなく、値の比較の方針・公理・属性・引用・旧名の互換を、契約ごとに明示する。**
8. **許可する未証明の入力（§6 を改める）。** 宣言・所有元・主張の指紋・引用・許可の範囲（直接か推移か）・主定理から届くことを期待するかを記録する。移行のときに見つかった sorry を、調整役とユーザーの追認なしに許可の一覧に入れない。

9. **速い方法と確かな方法を併用する（ユーザー決定 11-20）。** 成果物を直接読む方法の弱み：Lean の内部の形式に依る（版を上げると壊れうる）、成果物が古ければ古い内容を読む、公理の保存がない約 6.5 万宣言は別の経路になり継ぎ目で漏れうる、環境がないとできない検査（使われていない仮定、定義を展開した一致、実際に選ばれる instance）がある、道具を自前で保守する。そこで、日常は速い方法、裏付けとして遅いが確かな方法（import して Lean に計算させる）を、版を上げたときと定期的に全宣言で実行して比べる。食い違いがあれば速い方法を止める。読む前に全モジュールを建て、成果物とソースの対応を確かめる。未知は不合格にする。

### 新旧の一致（⑦ の実測）

Lean が保存している公理で比べると、旧い領域の監査 76 本の対象のうち保存のある 216,906 宣言で、判定の差は 0。残る 44,924 宣言は保存がなく、追加の照合が要る。本体全体では、保存のある 295,160 宣言のうち sorry に依るものは 164、許可外の公理は 0（調整役の採取の結果と一致）。旧い監査の対象の外では 18 宣言が sorry に依る（Kan–Quillen の引用とそれに依るもの）。

### 移行の順（レビューの §9）

1. 母集団・除外・許可の一覧を固定し、G1 の全対象の一覧を入れる。追跡の一覧と建った集合を一致させる。
2. Lean の公理・主張・値・直接の sorry の採取を、旧い監査と並べて走らせる。76 本の対象と許可の条件を同じコミットで出し、宣言ごとの判定が一致することを確かめる。意図した強化はユーザーの承認を得る。
3. G3・G4・G5 と適用の試験を用意する。改名・移動・削除・同名での主張の変更・一部のリンクの消失・禁止の依存・未供給の引用・落ちる適用例を実際に入れて、新しい検査が止まることを確かめる。
4. 日常の小さな変更、移動を含む変更、土台や外部パッケージを変える変更で、新旧を並べて走らせる。
5. スクリプトごとに、残る条件が移ったか、廃止が承認されたかを対応表（`research/audit-review/stage2-mapping.csv`）で確かめてから切り替える。一括の削除は別の承認にする。
